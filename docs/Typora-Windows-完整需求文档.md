# QTypora Windows 完整需求文档

本文件用于把 Typora Windows 的公开产品能力转化为 QTypora 的开发范围、界面规范和验收依据。**首发应用是 Windows 桌面 exe 及安装包，技术架构预留后续 macOS 版本**；前端指桌面界面与编辑引擎，后端指本地服务、主进程及原生能力。目标是覆盖桌面写作工作流、Markdown 编辑体验和本地服务能力，通过同版本实机对照实现功能与视觉一致。

调研日期：2026 年 9 月 30 日。用户确认首发为 **Windows 桌面端，并预留以后 macOS 打包与适配**。目前只有需求文档，没有应用代码或已经落地的技术栈。本次交付为需求研究，不包含应用实现；Mac 专有功能不纳入本次 Windows 功能验收。

## 1 研究基线和证据口径

### 1.1 版本和平台基线

本次读取的官方稳定频道首项为 **1.14.10**；1.14 功能公告发表于 2026 年 7 月 19 日，页面更新于 2026 年 9 月 6 日。需求以 **Windows 1.14 系列稳定版**为参照，实机验收前仍须记录安装包实际版本、架构和校验值。稳定频道没有为每个补丁列出发布日期，因此不推断 1.14.10 的发布时间。[稳定频道](https://typora.io/releases/stable)、[1.14 公告](https://support.typora.io/What's-New-1.14/)

Windows 系统基线采用 Windows 10、Windows 11。官网当前下载说明与 1.6 的停止支持公告均支持这一边界；系统需求页仍列 Windows 8，存在资料不一致，应以较明确的产品下载说明和版本公告为准。官网提供 x64、x86、ARM 下载入口；QTypora 应保留架构覆盖需求，交付次序见第 13 节。[官网](https://typora.io/)、[1.6 公告](https://support.typora.io/What's-New-1.6/)、[系统需求](https://support.typora.io/System-Requirements/)

### 1.2 什么算一比一

一比一需要同时满足以下四个维度，不能只以界面截图或 Markdown 渲染结果判定完成。

| 维度 | 比较内容 | 完成条件 |
| --- | --- | --- |
| 功能覆盖 | 命令、设置、文件工作流、扩展语法、系统入口 | 范围内能力全部实现并可访问 |
| 交互一致 | 输入、选区、光标、撤销、焦点、滚动、快捷键、异常处理 | 同一初始状态和操作序列得到对应结果 |
| 视觉一致 | 窗口、菜单、主题、排版、侧栏、浮层、导出页面 | 固定环境下逐场景比对通过 |
| 数据兼容 | 原始 Markdown、图片路径、编码、换行、导出格式 | 文档可互开，未触及的数据不意外丢失 |

当前已完成官方资料研究，**未完成 Windows Typora 1.14 的实机操作和像素测量**。官方截图可追溯，但本次浏览器图像预览未成功载入，不能声称已从截图准确量取颜色或尺寸。本文件是完整开发需求基线；其中待测项是精确复刻验收前的工作，不是已经验证的产品事实。

### 1.3 标记约定

| 标记 | 含义 | 使用方式 |
| --- | --- | --- |
| F | 官方专题文档或发行说明确认能力 | 表格中表示能力存在有直接依据 |
| L | 官方菜单或设置语言资源中出现 | 证明入口名称存在，当前 Windows 可见性、默认值和具体行为还要实测 |
| V | 尚待实机确认 | 不能当作 Typora 的既定行为实现后直接验收 |
| D | QTypora 的实施或验收设计 | 本文件制定的工程要求，不是 Typora 内部实现或性能实测数据 |
| X | 实验版或外部扩展能力 | 不并入 Windows 稳定版的完成率 |

后续功能表中的“依据”仅描述能力证据；**所有验收条件均是 D 类制定的测试要求**。涉及未公开行为的条件会附 V。专题来源在对应模块就近给出，完整资料索引见第 15 节。公开翻译资源混合了平台和历史入口，不能据此把所有文字都计为 Windows 功能。

优先级表示实现顺序：P0 为编辑和数据基础，P1 为完整工作流，P2 为长尾能力。**P2 仍属于完整复刻范围**，不能在最终交付中省略。商业授权体系和实验能力另列范围，防止与编辑功能混算。

## 2 产品范围和主要场景

### 2.1 产品定位

Typora 的核心是本地文件型 Markdown 编辑器，正文中融合编辑和预览；文档以普通文本保存在用户目录，图片使用外部文件或 URL 引用。多设备同步可交由 OneDrive、Dropbox 等第三方文件同步工具。[快速入门](https://support.typora.io/Quick-Start/)、[跨设备使用](https://support.typora.io/Sync/)

对 QTypora 的设计要求：未启用联网扩展时，用户可以离线新建、编辑、管理、搜索、保存和执行内建导出。文章的主数据是用户选择位置的 Markdown 文件。目录索引、偏好和草稿恢复数据属于应用辅助数据，不成为文章唯一存储位置。

### 2.2 用户和任务

| 用户 | 典型任务 | 所需完整工作流 |
| --- | --- | --- |
| 日常写作者 | 草稿、长文、日记 | 新建、混合编辑、专注、统计、保存、恢复 |
| 开发者 | README、技术方案 | 源码模式、代码、图表、链接、目录搜索 |
| 学生及研究者 | 课程笔记、公式、论文草稿 | 数学、脚注、编号、表格、PDF、Word |
| 内容运营 | 图文排版和传播 | 图片路径、上传、富文本复制、HTML、长图 |
| 本地知识文档用户 | 文件夹内阅读和维护 | 文件树、文章列表、大纲、快速打开、文件监视 |

### 2.3 范围边界

| 能力 | 当前判断 | QTypora 处理 |
| --- | --- | --- |
| 原生多标签页 | 官方快捷键表标明 Windows 不支持新建标签页 | 使用多窗口及打开文档切换；不自动添加标签栏 |
| 系统式历史版本浏览 | 官方明确 Windows 无此内建功能 | 复刻草稿恢复；完整历史版本可另立增强需求 |
| 文件操作撤销 | Windows 可撤销最后一次移动、重命名等；删除不支持此撤销 | 内容撤销与文件操作撤销分开管理 |
| 标签管理系统 | 官方明确不原生支持 `#tags` | 普通文本搜索兼容；不加入标签数据库 |
| 文本片段管理 | 官方明确不内建 snippets | 兼容第三方文本扩展工具输入 |
| 内建 Markdown lint 或格式化 | 官方明确无内建功能，可用转换或外部命令 | 提供相应扩展配置入口 |
| PDF 原生嵌入预览 | HTML 支持页标为不再支持 | 不计为必须内建的 PDF 阅读功能 |
| 图片对齐专用功能 | 官方说明无原生对齐功能，可由 CSS、HTML 达成 | 复刻布局和主题效果；不虚构图片对齐按钮 |
| 实时协作、云端文章库、双链关系图、AI 聊天 | 本次官方能力证据未确认 | 不自动纳入复刻要求；如增加应独立标记增强 |

边界依据：[快捷键](https://support.typora.io/Shortcut-Keys/)、[恢复](https://support.typora.io/Version-Control/)、[文件管理](https://support.typora.io/File-Management/)、[片段](https://support.typora.io/Text-Snippet/)、[转换](https://support.typora.io/Markdown-Export/)、[HTML](https://support.typora.io/HTML/)、[图片](https://support.typora.io/Images/)。

## 3 界面结构和前端风格

### 3.1 窗口结构

正文是视觉中心。主窗口由窗口标题和控制区、命令菜单、可切换左侧栏、单一正文编辑区、状态栏组成；查找、快速打开和上下文工具按任务出现。1.14 新增可开关的浮动编辑工具栏。[1.14](https://support.typora.io/What's-New-1.14/)、[Windows](https://support.typora.io/Typora-on-Windows/)、[文件管理](https://support.typora.io/File-Management/)

布局规格 D：上部为窗口与菜单，正文填充剩余空间；左侧栏开启时正文使用剩余宽度居中，关闭时恢复可用宽度。底部状态栏不遮挡最后一段。浮动工具不改变文章源文件。各区宽度和高度须按第 12 节固定环境实测。

### 3.3 视觉原则

以下为从产品定位和主题文档整理的设计要求 D，并非已测量的像素值。

1. 保持低装饰密度和大面积正文留白，正文周围使用简洁边界。工具控件的对比和尺寸服从任务层级。
2. 阅读状态优先显示格式化内容；正在编辑的局部语法采用次级色，避免让全部标记常驻正文。
3. 窗口壳和文章主题是两个可分别比较的对象。System Native 的系统标题栏行为与 Unibody 的应用绘制区域分别验收。
4. 文件树、菜单和设置采用紧凑信息密度；正文采用适合长文阅读的行距。表格、公式、代码和图表保持独立排版规则。
5. 鼠标悬停、当前项、键盘焦点和选区必须可区分；图标动作保留可访问名称及对应提示。
6. 暗色模式依赖主题，不能只把背景和文字反色。代码高亮、公式、图表、图片失败占位和菜单都要一起验收。

Typora 支持 CSS 主题、用户 CSS、原生与 Unibody 窗口样式相关界面资源；主题文档提供正文区域和常用颜色变量的定制方式。[主题编写](https://theme.typora.io/doc/Write-Custom-Theme/)、[设置资源](https://raw.githubusercontent.com/typora/Typora-i18n/master/Base.lproj/Panel.strings)

### 4.2 混合编辑核心

官方快速入门说明行内标记会智能隐藏或显示，块样式在输入或离开块时渲染；源码模式与混合模式在 1.13 改进为保留滚动位置。[快速入门](https://support.typora.io/Quick-Start/)、[1.13](https://support.typora.io/What's-New-1.13/)

2026-09-30 模式专项复核：Typora 默认正文使用 Live Preview，在同一界面阅读并直接编辑；
光标进入行内样式时局部展开标记，表格支持单元格直接编辑。Windows 默认 Ctrl+/ 在实时预览编辑与全篇源码之间切换，
Ctrl+E 对应样式范围/表格单元格选择。独立只读阅读请求在官方 issue #710 和 #6104 仍为 Open，
本次未找到已发布的 Windows 标准只读阅读切换说明，因此不能将“源码编辑 ↔ 只读阅读”称为 Typora 默认交互。

## 7 桌面前端与本地后端职责

### 7.1 交付形态

**QTypora 的交付对象是安装后在 Windows 独立运行的桌面程序、可执行文件和安装包。** 不以浏览器页面、网站地址、PWA 或需要启动开发服务器的演示作为最终交付。

“前端”是桌面界面及编辑引擎；“后端”是本地服务层、主进程或原生模块。基于后续 macOS 需求，建议采用 Electron、React 和 TypeScript，以及 Node.js 本地服务；构建和打包建议见第 7.6 节。编辑引擎仍须通过输入法、光标、剪贴板、导出、主题兼容和多窗口原型验证后冻结，不据项目名称推断使用 Qt。

本地核心不要求部署 REST 服务或启动独立网络端口。若选用进程间通信，接口仅提供已声明的桌面能力，并隔离文章渲染内容。下列职责是 **D 类黑箱能力拆分**，没有证据表明 Typora 内部采用同一架构。

### 7.3 数据与状态规则

以下全部为设计要求 D。

| 数据对象 | 应包含的信息 | 持久化和一致性要求 |
| --- | --- | --- |
| DocumentSession | 文档 ID、路径或未命名状态、原文、编码、换行、修订、已保存修订 | 路径不是唯一身份；异步结果绑定文档和修订 |
| EditorPosition | 选区方向、起止文本位置、所在块、滚动锚点 | 模式切换前后映射；DOM 索引不作为持久唯一位置 |
| WorkspaceState | 当前目录、展开项、侧栏类型、排序和过滤 | 不建立隐藏文章副本；目录变更时清理无效条目 |
| ResourceReference | 来源、解析基准、实际文件、引用位置及属性 | 资源操作和文章改写保持可恢复一致性 |
| SearchTask | 查询 ID、范围、选项、对应文本修订和结果 | 已取消或过期结果不覆盖新查询 |
| ExportProfile | 格式、依赖、主题、参数、变量和结束动作 | 项目有稳定 ID；名称相同不混用 |
| BackgroundTask | 任务 ID、文档 ID、状态、进度、输出和取消令牌 | 每个任务仅一次进入终态；关闭窗口规则明确 |
| DraftRecord | 草稿 ID、时间、原路径、内容及校验信息 | 恢复不覆盖原稿；备份读取可独立于编辑进程 |
| PreferenceRecord | 版本、作用域、设置项、值和生效方式 | 校验、迁移、错误回退；不删除未知字段 |
| WindowSession | 窗口 ID、文档关系、位置、缩放、模式 | 多屏恢复时约束到可见区域 |

文档状态至少区分：未命名、已保存、已修改、保存中、保存失败、外部变化、冲突、只读和关闭中。保存结果只能对应发起时的修订；保存期间发生新编辑后，仍应保留新修改状态。

任务状态至少区分：等待、运行、成功、带警告成功、失败、取消。任务结束后须报告已生成哪些文件，不能用一个“完成”提示掩盖批量部分失败。

### 7.4 本地错误契约

不在本需求阶段预定具体 IPC 方法名或 HTTP API。实现前需要为以下错误类别建立统一、可测试的本地契约。

| 错误类别 | 前端必须提供的信息 | 本地层必须保证 |
| --- | --- | --- |
| 文件不存在或被移动 | 原路径、重选或重新载入入口 | 不以空文本覆盖现有编辑内容 |
| 权限不足、文件锁、磁盘满 | 操作、受影响目标、可重试或另存为 | 不清除 dirty 状态 |
| 编码无效或解码失败 | 使用何种编码、重开入口 | 保留原始字节或取消打开 |
| 外部修改冲突 | 本地与磁盘版本区别及选择 | 不在后台擅自覆盖 |
| 转换器或上传器缺失 | 缺失组件和配置入口 | 不启动无关软件或自动执行安装 |
| 渲染或导出失败 | 格式、失败节点或工具输出 | 原文和旧目标文件不丢失 |
| 超时或用户取消 | 任务已停、是否有部分输出 | 停止子任务，不再改写引用 |
| 网络或认证失败 | 对应服务及重试方式 | 核心编辑仍离线可用 |

### 7.5 网络范围

文档核心不需要云端业务后端。可联网的范围为用户引用的远程资源、图片上传器、字典下载、外部帮助链接、自有更新，以及商业化时的自有许可与订单服务。第三方同步软件负责文件同步；QTypora 负责正确处理其写入的本地文件变化。

若实现收费，支付、授权、发票和管理站点是独立的商业配套能力；编辑器仍是桌面软件。不得把文章保存、文内搜索或基础导出转移成必须登录的服务器工作流。

### 7.6 跨平台技术栈与打包建议

2026 年 9 月 30 日补充范围：Windows 首发，技术架构预留未来 macOS。当前没有应用代码；下表是建议的技术基线 D，不代表已经实现或已经通过编辑器原型验证。Electron 支持共享 JavaScript 代码构建 Windows、macOS、Linux 桌面应用；本项目仍以 Windows 功能复刻为首发验收范围，macOS 专有功能另立需求。[Electron 官方介绍](https://www.electronjs.org/docs/latest)

| 层次 | 建议技术 | 本项目责任 D |
| --- | --- | --- |
| 桌面框架 | Electron | 窗口生命周期、系统菜单、文件对话框、剪贴板及系统集成 |
| 桌面界面 | React、TypeScript、CSS 主题变量 | 正文外围界面、侧栏、偏好、工具栏、亮暗主题和状态展示 |
| 混合编辑引擎 | ProseMirror 加自定义 Markdown 编辑层 | 原文保留、局部语法展开、选区、事务和撤销；必须先验证中文 IME 与位置映射 |
| 源码及代码编辑 | CodeMirror 6 | 源码模式、围栏内部编辑、语言高亮；完整旧主题兼容需要适配验证 |
| 本地后端 | Electron 主进程、Node.js、TypeScript | 文件读写监视、草稿恢复、资源管理、搜索及外部工具；重任务放入工作进程 |
| 前后端通信 | preload、contextBridge、受限 IPC | 只暴露声明的桌面操作，文章渲染内容没有文件系统和系统执行权限 |
| 内容渲染及转换 | MathJax、Mermaid、Pandoc 及专题对应旧图表引擎 | 依冻结版本支持集合适配；数学图表离线资源随包分发，Pandoc依赖策略另登记 |
| 开发构建 | electron-vite | 编译主进程、preload 和界面资源 |
| 应用分发 | electron-builder | 把构建资源、Electron运行时、图标和所需工具形成平台安装包 |

主进程运行于 Node.js 环境，界面渲染与主进程分开，通过受限桥接通信。这是可用于本产品的架构选择，不声称 Typora 内部采用 React 或 ProseMirror。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)

ProseMirror 和 CodeMirror 是编辑基础库；语法隐藏、光标跨格式边界、源文往返、复杂表格及模式切换仍需定制，不视为安装库即可完成的功能。ProseMirror 与 CodeMirror 的官方 GitHub 仓库已迁移到维护者的新托管站，应从官方渠道和包注册表冻结实际依赖来源及版本。[ProseMirror 官方仓库迁移说明](https://github.com/ProseMirror/prosemirror)、[CodeMirror 官方仓库迁移说明](https://github.com/codemirror/dev)

建议 Electron 的理由 D：统一渲染引擎便于跨平台比较主题、公式、图表和导出效果，TypeScript 可用于界面及本地服务。代价是包含 Chromium 和运行时带来的安装体积及内存开销；是否达到第 11 节预算仍需原型测量。React 管理外围界面，编辑器内部的文本、选区和事务由编辑引擎负责，不让每次 React 渲染重建正文。

打包流程 D：编译主进程、preload 和界面资源，再由 electron-builder 汇集运行时及资源，分别生成各平台产物，最后执行平台签名、校验和安装测试。采用工具稳定版本并锁定依赖；electron-builder 当前文档区同时提供稳定 v26 与预发布 v27，不能混用两代配置字段。[electron-vite 分发指南](https://electron-vite.org/guide/distribution)

| 平台 | 推荐产物 D | 架构计划 | 构建及验证环境 |
| --- | --- | --- | --- |
| Windows 首发 | NSIS 离线安装包 .exe，安装后运行 QTypora.exe | x64 首轮；ARM64 和 x86 分别复核运行时支持 | Windows runner 构建和安装卸载测试 |
| macOS 后续 | QTypora.app、DMG；启用自动更新时另提供 ZIP | Apple Silicon arm64 与 Intel x64；可评估 Universal 包 | macOS runner 构建、签名、公证及安装测试 |

Windows NSIS 和 macOS 目标由 electron-builder 支持。使用一个项目和统一工具并不等于只在 Windows 就能完成所有平台的正式发行；macOS 签名需要 macOS 环境，原生依赖也必须有目标平台及架构对应的产物。[NSIS 稳定版说明](https://www.electron.build/v26/docs/nsis/)、[macOS 稳定版说明](https://www.electron.build/v26/docs/mac/)、[跨平台构建](https://www.electron.build/v26/docs/features/multi-platform-build/)

正式向用户分发的 macOS 版本应规划 Developer ID 签名及 Apple 公证，所需开发者账号和凭据在实际发布阶段配置，不存入源码或文档。Mac App Store 分发属于另一个渠道，不由生成 DMG 自动满足。[Electron 签名及公证](https://www.electronjs.org/docs/latest/tutorial/code-signing)

跨平台实现规则 D：

1. 共享编辑器、Markdown模型、主题、资源及大部分本地逻辑；文件路径、用户目录、回收站、窗口、菜单、快捷键、打印及更新通过平台适配层处理。
2. Windows 的 Ctrl 与 macOS 的 Command、全局菜单、关闭窗口生命周期分别设计并测试，不能原样复制 Windows 壳。
3. 应用资源从正式安装目录读取；草稿、配置、字典和用户主题写入各平台用户数据目录；禁止硬编码 Windows 盘符和路径分隔符。
4. 原生模块、Pandoc及上传工具必须按平台与架构准备，不能把 Windows exe 塞进 Mac 包宣称兼容。可执行资源需要适当解包，不能只依赖 ASAR 虚拟目录。
5. CI 规划 Windows 和 macOS 两组构建任务；各安装包经过平台真机或可信环境验证后再发布。
6. x86 支持需单独核对 Electron 的版本与维护周期。不能为保留 32 位长期停留在失去安全维护的运行时；第 9 节架构要求在实现基线冻结时明确处理。
7. macOS 目前是架构预留，尚未把其专有菜单、系统版本历史等能力纳入本次 Windows 完成率；实际启动 Mac 版本时补齐专有需求和视觉基准。

## 11 非功能与工程质量要求

本节全部为 D 类要求，不代表 Typora 性能测量或内部实现。指标是 QTypora 研发启动时的初始验收预算；性能原型完成后可形成有记录的调整，不能用调低指标掩盖同环境下明显落后的体验。

### 11.1 性能预算

基准机暂定 D：Windows 11 x64、4 核 CPU、8 GB 内存、NVMe 存储、1920×1080 屏幕；记录具体硬件、系统版本、驱动、应用构建与主题。冷启动重复至少 10 次；编辑时延采样至少 100 次，报告 p50/p95、内存峰值和输入到绘制的测量口径。网络资源不计入离线正文首屏，但需报告异步加载状态。

| 编号 | 指标及目标 D | 测试边界 |
| --- | --- | --- |
| NFR-01 | 冷启动至可输入 p95 不超过 3 秒 | 本地空白文档；首次安装向导单列 |
| NFR-02 | 100 KB 常规文档可编辑 p95 不超过 0.8 秒 | 不含远程图片，清楚标注缓存冷热 |
| NFR-03 | 1 MB 混合文档可编辑 p95 不超过 3 秒 | 代码、表格、公式数量固定并记录 |
| NFR-04 | 常规打字输入到绘制 p95 不超过 100 ms | 普通段落及 1 MB 文档各测，中文合成独立测 |
| NFR-05 | 保存 1 MB 到本地盘 p95 不超过 1 秒 | 包含写入结果；同步盘延迟单列 |
| NFR-06 | 1 万 Markdown 文件约 100 MB 的首次文本搜索不超过 5 秒 | 无远程盘；可取消，后续增量结果不阻塞输入 |
| NFR-07 | 长文滚动与模式切换无持续冻结 | 记录超过 100 ms 的主线程阻塞和光标错位 |
| NFR-08 | 重复操作无持续内存增长 | 100 次打开关闭、切换模式、导出；结束后资源可回收 |
| NFR-09 | 后台任务不冻结编辑器 | 大目录搜索、图表渲染、图片上传和转换分别测试 |
| NFR-10 | 超大文档明确降级或提示 | 10 MB、超长单行及复杂图表压力样例；不损坏文件 |

内存预算应先测量原型与同环境 Typora，再冻结空白、常规和压力场景的上限；本次不写未经验证的“与 Typora 同样内存”结论。x86 和 ARM 的性能阈值使用各自基准机登记，不能套用 x64 测值。

## 12 验收方案和样例库

### 12.1 样例库构成

应创建版本化测试资料 D：普通 Markdown、严格与宽松语法、嵌套列表、复杂表格、各代码语言、公式及编号、各图类型、带元数据的图片、相对链接、HTML 媒体、多编码换行、导入源文件、每种导出目标、故障文件夹及恢复草稿。样例应有可复现步骤、源文本、预期磁盘变化和视觉基准，不只放一张截图。

编辑测试包含顺序操作和撤销回放：从原始文档 A 完成操作得到 B，撤销得到 A，重做得到 B；与磁盘操作相关的测试还需记录路径、资源和文件监视变化。混合编辑的输入过程中存在尚未完成语法，应另外保存过程状态。

### 12.3 视觉一比一验收

1. 冻结 Typora Windows 安装包版本、CPU 架构、主题文件、语言、设置、Windows 版本、显示缩放、文本缩放、字体和窗口样式。保存安装包哈希及测量记录。
2. 两应用使用同一 Markdown 和附件目录，采用同一窗口内容尺寸。至少取空白、长文、代码、表格、公式、图表、图片、大纲、搜索、工具栏和设置界面。
3. 单独记录默认、悬停、选中、聚焦、禁用、只读、错误、滚动末尾等状态；亮色和暗色分别取样。
4. 建立真实颜色、字重、字号、行高、宽度、间距、边界、图标和定位的 Token 表，替换第 3 节暂定值。正文滚动位置以同一标题或文本锚点校准。
5. 建议 D：主要固定边界误差控制在 1 CSS px 内；正文断行和表格列宽按相同字体环境比对。具体阈值在基准冻结后确认。字体抗锯齿和系统阴影需单独记录容差，不能掩盖字体、布局或主题差异。
6. 比较静态图片之外，回放输入、焦点、滚动和快捷键操作。渲染截图相同而输入事务、选区或磁盘结果不同仍判失败。

### 12.4 完成判定

所有已确认、范围内稳定版需求均有实现入口及通过的测试；P2 不能因优先级较低而算作已完成。每个 V 项需被实机确认、标明对应平台外或不可见条件，或形成经用户确定的范围决策。存在未完成 V 项时只能声明“研究基线完成”或“某阶段实现完成”，不能声明全量一比一已验收。

完成度分开报告：功能覆盖、交互一致、视觉一致、文件与转换兼容、Windows 架构覆盖。商业服务与实验能力另列，避免把实验功能凑入稳定版覆盖率或掩盖长尾功能缺失。

## 13 实施顺序和交付里程碑

这是需求后的实施安排 D，不是工期承诺。最主要的不确定性是混合编辑输入事务、中文 IME、源位置映射、表格行为、公式图表兼容和各格式转换，不能按普通内容网站工作量估算。

建议技术栈和跨平台打包方案见第 7.6 节。先通过 M1 验证中文输入、源文往返、表格、光标映射、导出及内存，再冻结具体编辑器依赖与版本。Windows 首发功能范围保持，macOS 作为后续适配平台；共享代码与平台差异分别测试。

最终应用交付清单 D：各承诺架构的 exe 和安装包、版本及校验记录、完整功能与设置清单、菜单快捷键、主题与字体依赖、帮助文档、迁移与恢复说明、测试样例、视觉基准、兼容及降级列表、性能测量、安装卸载升级验证、开源依赖及资源声明。源码和服务部署内容的交付方式在启动实施时确定。
