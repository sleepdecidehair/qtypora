# 故障复盘：Windows 8.3 路径导致文档监听进程崩溃

## 基本信息

| 字段 | 内容 |
| --- | --- |
| 日期 | 2026-09-30 |
| 发现环节 | 首轮桌面文件服务单元测试 |
| 严重程度 | P1：进程原生终止 |
| 影响范围 | 以 8.3 短路径打开或保存后启动文档目录监听的 Windows 开发环境 |
| Issue / 提交 | 当前工作区未初始化 Git，未提交 |

## 问题描述

运行 `npx vitest run src/main/files.test.ts src/main/documents.test.ts` 时，文件读写测试通过，文档服务测试所在子进程原生终止，测试没有正常结束。单独运行 `retains newer edits` 保存竞态测试可稳定复现；只测试没有磁盘监听的新文档恢复用例正常通过。

日志关键内容：

```text
Assertion failed: !_wcsnicmp(filename, dir, dirlen), file src\win\fs-event.c, line 72
Worker exited unexpectedly with exit code 3221226505
```

## 根因与证据

1. 当前 Windows 用户环境的 `os.tmpdir()` 返回 `C:\Users\ADMINI~1\AppData\Local\Temp`，目录包含 8.3 短名称。
2. 只执行没有 `fs.watch` 的新文档草稿测试不崩溃；完成磁盘保存并开启父目录监听后触发上述 libuv 断言，因此不是文件编码或 Vitest 断言失败。
3. 在相同路径上，`fs.promises.realpath` 和 `fs.realpathSync` 仍返回短名称；`fs.realpathSync.native` 返回 `C:\Users\Administrator\AppData\Local\Temp`。
4. 原实现把短路径父目录交给 `fs.watch`。底层 Windows 文件事件报告长路径，而 libuv 的路径前缀断言比较短目录与长文件名，导致原生终止，JavaScript `try/catch` 无法捕获。
5. 最初只做了普通 `path.resolve` 和 promises `realpath`，错误地把两者视为 Windows 短名称完全规范化。该问题直到真实 Windows 临时目录单元测试才暴露。

相关代码：`src/main/files.ts` 的 `canonicalPath`、`canonicalInside`；`src/main/documents.ts` 的 `open`、`save`、`startWatch`；`src/main/index.ts` 的 `openFolder`。

## 解决方案

统一采用 `fs.realpath.native` 解析已存在路径；保存新文件时先将父目录转为原生规范路径，再连接文件名。开启监听前再次以 `fs.realpathSync.native` 处理父目录。所有授权根、文档路径与监听目录使用同一规范形式，保留文件变化检测能力。

没有通过关闭监听、跳过测试或捕获不到的异常重试规避问题。

## 验证与预防

- 最小保存竞态用例从原生终止恢复为通过。
- 后续 `npx vitest run src/main`：3 个文件、22 个测试全部通过，无未处理错误。
- `npm run typecheck` 通过。
- 保存服务测试覆盖原生规范路径、并发快照、磁盘冲突和重命名后脏草稿；后续增加 Windows 路径逻辑时继续使用同一 `canonicalPath` 入口。
- 正式 Windows / macOS 打包和版本升级时，仍需实际操作文件监听；本轮仅验证 Windows 开发环境。

Windows 文件监听所用路径必须展开 8.3 名称，普通 `resolve` 或非 native `realpath` 不足以保证这一点。
