## 1. 问题描述

文章含 `# POSITION_5` 时，大纲显示 `POSITION5`；含 `file_name` 或行内代码标识符的标题也会丢失下划线。
点击大纲仍按原文行号跳转，但展示的标题与正文不一致。此前没有运行时异常；问题由联调文字比较发现。

代码证据是旧的 `Sidebar.tsx` 标题提取逻辑：

```ts
match[2].replace(/[*_`]/g, '')
```

该表达式把 `POSITION_5` 确定地转换为 `POSITION5`，并不判断这些字符是否属于 Markdown 格式语法。

## 2. 临时解决方案

未采用替换文章文字、关闭大纲或重新启动用户窗口等临时方案。问题只在导航派生数据中修复。

## 3. 根本原因分析

1. 正文源码保存了 `POSITION_5`，因此排除文档保存及编辑器模型改写。
2. 大纲独立提取标题文本；检查派生函数发现统一删除所有 `*`、`_` 和反引号。
3. Markdown 里的这些字符既可能是格式分隔符，也可能是普通字符、转义字符或行内代码内容。
4. 原算法没有语法上下文，无法区分这些情况，是展示错误的直接原因。
5. 大纲当时没有独立回归用例，只用普通中文标题验证，未覆盖代码标识符和转义字符。

## 4. 解决方案

在 [outline.ts](../../src/renderer/hooks/outline.ts:17) 中使用 `markdown-it` 的块级标题 token 和行内 token。
保留 `text`、`code_inline` 的原文本，提取图片替代文字与链接标签，忽略真正的格式分隔 token；
使用标题 token 的 `map` 保留原文行号。[Sidebar.tsx](../../src/renderer/components/Sidebar.tsx:24) 只消费该派生函数。

```ts
if (token.type === 'text' || token.type === 'code_inline') return token.content
```

修改不写文章内容，也不改变文档 ID、光标和保存基线。导航显示仍是纯文本，不执行标题里的 HTML。

## 5. 预防措施与验证

- 已增加 [outline.test.ts](../../src/renderer/hooks/outline.test.ts:1) 的 8 个回归场景：字面下划线、实际格式、转义字符、代码内容、链接与图片标签、代码围栏、Setext/引用标题行号、实体与 HTML 以及无效标题。
- `npx vitest run src/renderer/hooks/outline.test.ts`：1 个文件、8 条用例通过。
- `npm run typecheck`：通过。
- 后续大纲过滤、定位和锚点实现继续使用解析结果，不重新采用全字符删除的正则。
- 本轮真实 Electron 大纲点击与模式回归由根代理统一执行；本文不把尚未执行的新桌面用例计为通过。

## 6. 经验总结

Markdown 展示文本应由语法 token 派生，不能将可能充当格式标记的字符一律删除。
