# 故障复盘：文档状态与保存基线不一致

## 基本信息

| 字段 | 内容 |
| --- | --- |
| 日期 | 2026-09-30 |
| 发现环节 | 文件状态审查、单测和真实 Electron 联调 |
| 严重程度 | P1：可能丢失尚未保存的内存内容或产生错误冲突判断 |
| 影响范围 | 保存对话框延迟、外部删除/重命名、重新载入及关闭 |
| Issue / 提交 | 工作区未初始化 Git，未提交 |

## 根因与证据

这些问题共同源于将磁盘元数据、最近保存的快照和最新编辑内容混为同一状态：

- 保存对话框返回时，界面可能已经有新输入。直接用保存响应覆盖正文会丢失较新的输入；
  后端若不记录 savedRevision，晚到的旧保存也可能覆盖新保存。
- 外部删除未修改的文件后，原“正文等于 savedContent”判断仍认为干净；关闭可能丢弃唯一的内存副本。
- 重命名同步路径时若用整个 DocumentRecord 重置正文，会覆盖未保存输入。
- 重新载入若仅更新界面，不更新桌面服务的版本哈希，随后保存会产生伪冲突。

单测分别覆盖并发快照、原生路径、外部文件状态和脏草稿；真实窗口测试使用延迟 1.2 秒的
保存对话框验证之后的输入被保留，并模拟磁盘删除、重命名和重新载入。

## 解决方案

保存捕获具体 revision，响应仅更新对应保存基线，后续编辑继续保持 dirty。
桌面服务跟踪 currentContent、savedContent、revision、savedRevision、fileMissing 和磁盘 version。
旧保存不能越过较新的 savedRevision；缺失文件强制保留草稿并触发关闭保护。
重命名事件仅同步 id/path/name，不替换界面正文。
重新载入显式通过桌面服务重建磁盘哈希和基线，再更新界面。
保存、草稿和关闭操作串行或使用锁，错误通过共同 Result 契约传递。

## 验证与预防

- 延迟保存只写入捕获快照，较新的输入和独立草稿仍在；再次保存写入最新内容。
- 删除后出现提示和 dirty 标记，关闭取消后内存副本仍在，可另存为恢复。
- 文件树重命名后标题和路径更新，未保存正文不变，保存写入新路径。
- 明确重新载入后编辑保存成功，不出现伪冲突。
- 原生窗口关闭取消后可继续编辑，异常退出后恢复独立草稿。

Windows 撤销/重做回归使用 Ctrl+Z / Ctrl+Y。早期测试使用 Ctrl+Shift+Z 未触发 Windows
CodeMirror 的重做映射，是测试键位错误，不能据此归因为保存损坏历史。

以后每次文档状态变更都需要明确更新的是正文、磁盘元数据还是保存基线，
并用异步返回晚于用户输入的场景验收，不能只验证同步成功路径。
