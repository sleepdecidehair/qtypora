## 1. 问题描述

第一轮标准打包运行 `20261001-115149-925fd5b8` 中，终端显示 Node、npm、Vitest 和 electron-builder 的输出，`logs/pipeline.log` 却主要只保存阶段标题。预期是产物随附日志能够复核成功与失败信息。

证据：首轮日志包含 `--- Unit tests ---`，没有对应的 `223 passed`。终端仍有单元测试与编译结果；独立 JSON 测试报告正常，排除了测试未运行的可能。

## 2. 临时解决方案

保留首轮暂存与 JSON 记录用于诊断，不把未经全部检查的暂存产物交付。修复后重新执行统一入口。

## 3. 根本原因分析

1. 对比终端输出和 PowerShell transcript，确定丢失的是原生命令输出。
2. 检查 `scripts/package-internal.ps1:33` 的 `Invoke-Step`：直接执行外部程序，没有把输出送入 PowerShell 的显示管道。
3. 在 `.debug/logging-probe.ps1` 使用真实 Windows PowerShell 5.1 启动 Node，分别输出 stdout / stderr 并退出 7；通过 `2>&1 | Out-Host` 后，两种输出均进入 transcript，退出码仍为 7。

直接原因是把终端可见输出等同于 transcript 可捕获输出。设计遗漏了原生进程与 PowerShell 管道的区别；早期语法、类型和构建检查没有检验日志内容，因此直到产物检查时才发现。

## 4. 解决方案

`Invoke-Step` 将外部命令改为 `& $Executable @Arguments 2>&1 | Out-Host`。仅在执行期间使用 `ErrorActionPreference=Continue`，随后恢复原设置；外部程序 stderr 可能只是警告，是否成功以保存的原始退出码为准，非零即终止流程。

影响限定在命令执行与日志记录，不改变测试、编译、签名参数和产物检查。

## 5. 预防措施

- 真实运行 stdout / stderr / 非零退出码探针，避免仅检查脚本语法。
- 成功产物同时保存 transcript、单元测试 JSON 和桌面测试 JSON；根据 JSON 拒绝空跑、跳过和失败。
- 交付前抽查日志中实际的测试、构建、签名和桌面验证输出。

## 6. 经验总结

原生命令输出可见并不表示已写入 PowerShell transcript；日志内容和退出码都需要真实验证。
